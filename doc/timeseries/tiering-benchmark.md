# 계층화 전/후 실측 — 운영 테이블 형태

계층화를 켜기 전과 후를 **같은 이미지·같은 노드 설정·같은 데이터·같은 CQL**로 측정한 결과입니다.
스크립트: [`docker/scale-test.sh`](../../docker/scale-test.sh)(베이스라인) ·
[`docker/tiering-bench.sh`](../../docker/tiering-bench.sh)(계층화). 원자료(하네스 출력 전문):
[베이스라인](tiering-bench-baseline.md) · [계층화 후](tiering-bench-tiered.md).

**결론 먼저: chunk format v4에서 계층화는 저장과 질의 양쪽에서 이깁니다** — 디스크 **7.1× 절감**,
집계 **3~6× 가속**. 시간 범위를 걸지 않은 조회·행 단위 조회·static 조회를 포함해, 측정한 모든
질의에서 계층화 후가 같거나 빠릅니다. "저장을 아끼는 대신 질의가 느려진다"는 트레이드오프는
없습니다.

## 측정 조건

| 항목 | 값 |
| --- | --- |
| 호스트 | **234** — Xeon Silver 4114T (Skylake-SP, 40 threads, 250 GB RAM), 단일 노드 도커 컨테이너 |
| 이미지 | `aster-tsdb:6.0.0-v4wired` (CI와 동일 베이스, chunk format **v4**, master `5cbdf914fa`) · 2026-08-04 |
| 테이블 형태 | `tm_tag_point` — 파티션 키 `tag_id`, 클러스터링 `timestamp DESC`, static 7개, 일반 컬럼 8개 |
| 행 수 | **20,000,000** |
| 태그(파티션) | **500개**, 태그당 **40,000행** = 1초 간격 11.1시간 |
| 값 컬럼 | static `type`이 어느 컬럼을 채우는지 결정 — 숫자형 태그는 `value_numeric`, boolean 태그는 `value_boolean`, `value`(text)는 판독값의 문자열 사본 |
| 집계 컬럼 | **`value_numeric`** (`type='double'` 태그) — 실제 대시보드가 집계하는 컬럼 |

## 질의 시간

같은 CQL, 같은 결과값 — 두 실행의 결과 첫 행 값이 전부 일치함을 확인했습니다(정합성 교차 검증).
비율은 `전 ÷ 후` — 1보다 크면 계층화가 빠릅니다.

### 집계 (단일 파티션, 40,000행)

| 질의 | 비계층 | 계층화 v4 | 비율 |
| --- | --- | --- | --- |
| `count(*)` | 303 ms | **50 ms** | **6.1×** |
| `time_bucket 1h + avg/min/max` | 270 ms | **56 ms** | **4.8×** |
| `time_bucket 5m + avg` | 178 ms | **52 ms** | **3.4×** |
| `first`/`last`/`delta`/`rate` per hour | 198 ms | **64 ms** | **3.1×** |
| `derivative` per hour | 181 ms | **51 ms** | **3.5×** |
| `percentile` p50/p95/p99 | 194 ms | **41 ms** | **4.7×** |
| `variance`/`stddev` | 150 ms | **31 ms** | **4.8×** |
| `histogram` 20버킷 | 169 ms | **34 ms** | **5.0×** |
| `approx_count_distinct` | 161 ms | **38 ms** | **4.2×** |
| `integral + time_weighted_average` | 171 ms | **43 ms** | **4.0×** |
| `OHLC + change + p95` (대시보드 종합) | 199 ms | **82 ms** | **2.4×** |
| 컬럼 존재 확인 (`count(col)` 6종) | 195~200 ms | **60~65 ms** | **~3.2×** |

| gap-fill | 비계층 | 계층화 v4 | 비율 |
| --- | --- | --- | --- |
| `gapfill 1h + locf` (11.1h 전 구간) | 284 ms | **53 ms** | **5.4×** |
| `gapfill 5m + interpolate` (6h) | 162 ms | **30 ms** | **5.4×** |

| 멀티 파티션 | 비계층 | 계층화 v4 | 비율 |
| --- | --- | --- | --- |
| 10개 태그 시간별 avg (40만 행) | 1,620 ms | **478 ms** | **3.4×** |
| 90개 태그 시간별 avg (360만 행) | 14,940 ms | **4,216 ms** | **3.5×** |
| 90개 태그 태그별 p95 (360만 행) | 14,173 ms | **2,619 ms** | **5.4×** |

빨라지는 이유는 경로의 구조입니다 — 40,000개 행을 SSTable에서 낱개로 읽어 셀 단위로 병합하는
일반 경로보다, 창당 청크 몇 개를 컬럼 단위로 디코드해 배열에서 행을 조립하는 경로가 근본적으로
쌉니다. 데이터가 7.1× 작으니 IO·역직렬화가 지배하는 집계에서 이득이 그대로 나타납니다.

### 행 단위 조회 — 여기서도 계층화가 같거나 빠릅니다

| 질의 | 시간 범위 | 비계층 | 계층화 v4 | 비율 |
| --- | --- | --- | --- | --- |
| 최신 1,000행 `SELECT *` (boolean 태그) | 없음 | 56 ms | **45 ms** | 1.2× |
| 최신 1,000행 `SELECT *` (double 태그) | 없음 | 52 ms | **38 ms** | 1.4× |
| 1시간치 `SELECT *` (3,600행) | 있음 | 159 ms | **138 ms** | 1.2× |
| 1시간치 `timestamp+value`만 투영 | 있음 | 56 ms | **33 ms** | 1.7× |
| 1시간치 `timestamp+value_numeric`만 투영 | 있음 | 55 ms | **30 ms** | **1.8×** |
| static 컬럼만 1행 | 없음 | 7 ms | **4 ms** | 1.8× |

시간 범위 없는 `LIMIT` 조회는 창 목록을 payload 없이 나열해 두고 질의 방향 순서로(DESC면 최신
창부터) 한 창씩 페치·디코드하므로, `LIMIT`이 채워지면 나머지 창은 읽지 않습니다. 그래서 범위가
없어도 느려지지 않습니다. 시간 범위를 거는 습관은 여전히 좋습니다 — 해당 창만 디코드하므로
스캔량이 최소가 됩니다.

## ⚠️ 파티션 키 없는 집계는 실제 행 수를 돌려주지 않습니다

| 질의 | 비계층 | 계층화 v4 |
| --- | --- | --- |
| `SELECT count(*)` (파티션 키 없음) | 82,050 ms → `20000000` | **16 ms → `500`** |

**가속이 아니라 오답입니다.** 레인지 스캔은 청크를 병합하지 않으므로, 전부 계층화된 테이블에서
파티션 키 없는 집계는 **클러스터링 행을 하나도 보지 못합니다.** 여기서 나온 `500`은 태그 수입니다 —
static 컬럼은 청크화되지 않아 태그마다 static 행 하나가 남고, 그것만 세어진 값입니다.

> **`0`보다 위험합니다.** 0이면 뭔가 잘못됐다는 게 바로 보이지만, `500`은 "태그가 500개니까
> 맞나?" 싶은 그럴듯한 숫자입니다. static 컬럼이 없는 테이블에서는 `0`이 나옵니다 — 어느 쪽이든
> 실제 행 수(20,000,000)와는 무관합니다. 클라이언트 경고가 나가지만 대부분의 드라이버는
> 노출하지 않습니다. 투입 전 애플리케이션 점검 항목입니다 —
> [프로덕션 체크리스트](production-rollout.md).

## 해석과 적용 범위

- **`hot_window` 안쪽 질의는 비용이 없습니다.** 질의 범위가 콜드 경계 위에서 시작하면 병합 자체를
  건너뛰고 핫 이터레이터를 그대로 돌려줍니다. 위 수치는 `hot_window 1h`로 **전 구간을 콜드로
  만든** 최대 부하 조건입니다. 실제 운영에서 `hot_window`를 대시보드 구간에 맞추면 그 구간 질의는
  계층화 전과 동일합니다.
- **형태에 따라 이득의 크기가 다릅니다.** 저장 절감은 "컬럼이 여러 개이고 그중 상당수가
  상수이거나 전부 null인가"에 크게 좌우됩니다 (`quality`·`error_code`·`attribute` 고정, static
  `type`에 따라 `value_numeric`/`value_boolean` 중 하나가 통째로 비는 구조가 컬럼 지향 청크의
  설계 의도 그대로입니다). 접을 컬럼이 없는 최소 형태 — 고엔트로피 `double` 컬럼 1개짜리 —
  는 v4 기준으로 아직 재측정하지 않았습니다. 도입 전 자기 테이블 형태로 재보길 권장합니다.
- 초당 처리량(rows/s·ops/s) 관점의 수치는 [rw-throughput-benchmark.md](rw-throughput-benchmark.md)에
  있습니다.
